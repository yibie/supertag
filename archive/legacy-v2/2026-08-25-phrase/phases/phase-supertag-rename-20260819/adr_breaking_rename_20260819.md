# ADR：Supertag 破坏性改名

## Context

项目入口与少量公共配置仍使用 `org-supertag`，但大部分命令和模块已经使用
`supertag`。双重命名影响安装、配置、Babel、文档和未来 Agent 接口。

基线盘点显示 tracked 文件中有 191 个文件、1032 行旧名称匹配；其中大量位于
历史 phase 与 Changelog，不能靠盲目全局替换决定语义。

## Decision

- 6.0.0 建立 `supertag` 唯一命名，不提供运行时兼容层。
- 用户人工迁移数据目录；程序只负责在默认新旧目录冲突时失败保护。
- 当前运行时、文档和测试全面切换；结项历史材料保持原始事实。
- GitHub 仓库改名是最后一步，不作为代码迁移的前置依赖。

## Alternatives

### 保留一个主版本兼容层

拒绝。它延长双重接口生命周期，并要求长期测试旧入口、alias 和 Babel 名称。

### 自动搬迁数据目录

拒绝。程序无法安全判断其他 Emacs 实例、锁文件、备份状态和两个目录的所有权。

### 盲目全仓字符串替换

拒绝。历史事实、迁移说明、路径、Lisp 接口和普通品牌文本需要不同处理。

## Consequences

- 用户必须一次性修改配置、Query Block、安装源与数据目录。
- 外部插件若依赖旧符号会直接失败，必须同步升级。
- 运行时代码与当前文档获得一个可推断的唯一词汇。
- 历史材料仍可能命中旧名，最终审计必须使用明确白名单而非零匹配计数。

## Rollback

GitHub 改名前可 revert 对应 task 提交。数据由用户显式备份和改名，程序不执行
不可逆移动。GitHub 改名后若需要回退，必须同时恢复仓库名、remote 和公开文档。
